# BABAI flow architecture matrix

## Purpose and status

This is the durable flow-by-flow architecture handoff for BABAI. It turns the
founder-flow discussion into explicit ownership, contracts, reliability and
pilot gates without claiming that a backend implementation or provider
approval already exists.

The request named thirteen flows but asked for fourteen families. The
fourteenth family is made explicit here as **identity / tenant / channel /
entitlement**, because every other flow depends on trusted context resolution
and tier authorization. Billing-account and subscription transitions are part
of that family and the onboarding family; they are not allowed to become an
implicit shortcut around domain authorization.

Architecture status uses:

- **Specified** — ownership and contract direction are documented below and
  in the linked architecture/domain documents.
- **POC/pilot gate** — required to validate the first paid pilot or a
  controlled-beta expansion.
- **Later** — deliberately not a first-pilot dependency.
- **Implementation/demo** — this branch contains architecture documentation,
  not a running BABAI backend. Unless stated otherwise, implementation is
  **not started** and no executable product demo is claimed.

Raw-founder citations use both exact source locations:

`Raw T<number> (<mapping/message UUID>); nekurama.raw.chat.json:L<line>; nekurama.chatgpt.md:L<line-range>`.

The raw JSON line is the mapping object in the committed current revision.
The readable Markdown line range is a companion locator, not a substitute for
the UUID. Assistant turns are retained as decision history; founder-authored
turns remain primary evidence where the source distinguishes them. `01 /
THE MOCK FLOW` is intentionally excluded.

## Cross-cutting contract used by every family

```text
Inbound webhook / web action / worker command
  -> authenticate and verify provider/request context
  -> resolve identity, billing account, tenant, branch, channel and actor
  -> load entitlement and policy version
  -> enforce capability, quota and provider admission
  -> validate the owning aggregate transition
  -> PostgreSQL transaction:
       authoritative state transition
       outbox record
       required audit/provenance record
  -> bounded command result
  -> managed queue / worker side effects
  -> idempotent consumers, notifications, reconciliation and metrics
```

Every command/event should carry, subject to classification:

`eventId`, `eventType`, `schemaVersion`, `occurredAt`, `recordedAt`,
`producer`, `tenantId`, `branchId`, `channelId` where applicable, `actorRef`,
`aggregateType`, `aggregateId`, `correlationId`, `causationId`, `flowId`,
`idempotencyKey`, `classification`, and a typed payload or payload reference.

The baseline is at-least-once delivery with transactional outbox, inbox/
deduplication, bounded retries, quarantine/DLQ, authorized replay and
provider reconciliation. A failure must never become success-shaped domain
state. Payment, order and fulfillment are separate state machines. Human
takeover pauses conversational automation only; it does not pause, rewrite or
silently bypass order, payment, fulfillment, authorization, outbox or
reconciliation processing.

## Non-negotiable cross-family invariants

1. **Payment is not order.** Payment completion, payment failure, manual
   confirmation, refund and reconciliation update `Payment`; only the Order
   aggregate can accept/reject or progress an order. A payment callback cannot
   accept an order, and an order callback cannot mark a payment paid.
2. **Human takeover is conversation-scoped.** Automation is paused or
   suppressed for the conversation while human ownership is active. Order,
   payment, fulfillment, timers, outbox/inbox processing and reconciliation
   continue independently. Releasing a conversation does not replay stale
   automated messages without a fresh context check.
3. **Pickup is the first fulfillment.** Pickup requires no customer address and
   is the fallback only when the customer explicitly accepts it. Delivery is
   an optional provider-backed capability, tier-gated and unavailable until
   quote/booking/status behavior is validated.
4. **Promotions and combos are tier-gated.** LITE has no promotion/combo
   workflow; BASE has bounded deterministic controls; PRO has higher/advanced
   controls only after policy, quota, abuse, tax/rounding and provider/channel
   evidence. An unavailable tier is an explicit non-success outcome.
5. **Direct merchant settlement.** Customer money goes to the merchant via a
   validated UPI/gateway/manual path. BABAI does not introduce a wallet,
   escrow or customer-funds custody layer in the pilot.
6. **AI is advisory.** Extraction, intent, recommendations and drafts become
   typed commands and pass authorization, policy, deterministic validation and
   human approval where required. AI cannot choose tenant, branch, entitlement,
   order, payment, refund, fulfillment, consent or external side effects.
7. **Historical truth is frozen.** An order stores its commercial result,
   applied benefits, tax/rounding inputs and menu revision. Later menu,
   promotion, price or provider changes do not rewrite the order.
8. **Events are not state.** Events, workflow records, audit and telemetry
   coordinate or describe the system. Aggregate state and validated
   transitions remain authoritative.

## Acceptance and observability gates

The matrix is accepted for design handoff only when the implementation plan
preserves these gates:

- **Boundary:** wrong tenant, branch, role, entitlement or consent is rejected
  explicitly and appears in audit/metrics.
- **State:** every accepted transition has a version/precondition, an atomic
  authoritative write, outbox record and required audit record.
- **Reliability:** duplicate inbound/provider events, worker restarts and
  retries do not create duplicate orders, payments, bookings or messages.
- **Failure:** timeout/unknown, non-retryable validation, human-action and
  provider reconciliation cases remain visibly distinct; no success-shaped
  fallback is permitted.
- **Human safety:** active takeover suppresses automation while independent
  order/payment/fulfillment processing remains correct.
- **Commercial integrity:** order snapshot is reproducible; payment amount,
  merchant and currency are verified; direct settlement is observable.
- **Tier integrity:** LITE/BASE/PRO checks happen server-side at gateway,
  worker and owning module; quotas are atomically consumed or explicitly
  denied.
- **Continuity:** pilot evidence includes daily backup success, tested restore,
  initial RPO 24 hours and RTO 8 hours.
- **Pilot instrumentation:** activation, order conversion/completion, pickup
  completion, staff adoption/takeover, support effort, provider/API cost,
  failure/refund cost, repeat use and tier adherence are captured per
  tenant/branch.

Minimum alert set: failed backup, oldest outbox/queue age, DLQ/quarantine
growth, callback verification failures, ambiguous payment settlement,
delivery/provider failure spikes, projection lag, suspected scope violation,
automation-suppression violation, and founder-support capacity pressure.
